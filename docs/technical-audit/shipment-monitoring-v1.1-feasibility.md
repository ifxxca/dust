# Shipment Monitoring V1.1 — feasibility audit and verified increment

Date: 2 November 2026. Repository: `S:/2026/dust`.

## 1. Executive summary

**FEASIBLE WITH LIMITATIONS.** The repository already supports persistent AWB snapshots, repeat batch-AWB APEX collection, source provenance, chronological snapshot projection, and separate reconciliation history. A useful read-only monitoring increment is implemented using that pipeline. No collector, polling cadence, queue configuration, infrastructure, migration, or deployment was added.

The verified subset is report-based status monitoring. It is not a real-time courier feed, complete courier-event timeline, or verified failed-final classifier. DELIVERED and explicit AWB cancellation retain the existing conservative tracking baseline. RETURNED, failed delivery attempts, unknown statuses and generic FAILED remain open. Verified custom tracking policies remain independent and unchanged.

The increment adds an admin-only list/detail interface, server pagination and filters, separate source-status/snapshot/receipt timestamps, optional user-selected freshness thresholds, and deterministic comparison of status evidence. Identical or formatting-equivalent evidence produces no additional status transitions; every distinct imported source row still has an observation. Older snapshots remain evidence without replacing newer current state. Corrections can reopen terminal shipments.

Final relevant runs: **149 backend tests / 1,057 assertions passed**, including **21 new monitoring tests**; **55 existing frontend tests and one new browser regression script passed**. Frontend type checks, scoped lint, scoped PHPStan, build and dirty PHP formatting pass. Repository-wide PHPStan still fails on seven diagnostics in two unchanged files; this is an explicit release-check limitation. No 20-user capacity claim is made.

### Identity and deduplication

`ImportReportAwbs` uppercases/validates AWBs without converting them to numbers, retaining leading zeroes. Within one file, identical normalized duplicate rows are counted once; conflicting duplicates reject the import. The unique `(report_job_id, awb)` key prevents duplicate source records on replay. `2026_10_24_150411_enforce_unique_awbs_on_jne_shipments.php` establishes global registry AWB uniqueness: account is attribution evidence, not a separate shipment identity. The previous account/AWB unique index remains. Cross-report duplicates retain distinct evidence and one registry record. Normalized/raw account values and ambiguous customer evidence remain separate.

## 4. Status mapping and terminal semantics

| Raw evidence already supported                                                        | Normalized status         | Conservative tracking treatment                           |
| ------------------------------------------------------------------------------------- | ------------------------- | --------------------------------------------------------- |
| `AWB_CANCEL` Y / YES / 1                                                              | CANCELLED, takes priority | Terminal baseline                                         |
| DELIVERED, TERKIRIM, `DELIVERED TO [` prefix, or POD DELIVERED                        | DELIVERED                 | Terminal baseline                                         |
| RETURNED, RETURNED TO SHIPPER, bracketed return description                           | RETURNED                  | Non-terminal pending approved return semantics            |
| POD UNDEL / UNDELIVERED; incomplete address, unknown recipient, recipient not home    | EXCEPTION                 | Non-terminal, failed delivery attempt is not failed-final |
| Existing received/departed/processed/forwarded/courier/on-process/in-transit prefixes | IN_TRANSIT                | Non-terminal                                              |
| Generic FAILED, Error On Push, other unmapped/empty statuses                          | UNKNOWN                   | Non-terminal; do not fabricate failed-final semantics     |

The existing general `TERMINAL_STATUSES` includes RETURNED for other reporting use cases. It is deliberately not changed. `TRACKING_TERMINAL_STATUSES = ['DELIVERED', 'CANCELLED']` names the existing default refresh rule; `QueryActiveJneAwbs` now references that constant with identical selection behavior. No new failed-final status is introduced. The API reports `failed_final: null`; the UI explains its unavailability rather than displaying a fabricated zero.

Verified custom policies in `ManageJneRefreshPolicy` can specify terminal status sets and chronological distinct-observation confirmations; activation requires verified policy evidence and the existing environment gate. No policy was enabled or changed. The new screen labels the conservative baseline, explicitly disclosing that a custom pulling policy can differ. It does not claim to show policy confirmation completion or live polling eligibility.

Current-state authority remains effective snapshot `observed_at`, followed by greater report-job ID for equal times. An old snapshot cannot replace a newer one merely because it arrived later. Nullable source-event timestamps are displayed, not promoted to a universal ordering contract. Newer corrective snapshots may change DELIVERED/CANCELLED back to an open status. No terminal state is made irreversible.

## 5. Bottlenecks, historical fixes and remaining integration risks

Reviewed the existing storage investigation, worker recycle review, cross-customer remediation, jobs/integrations and reconciliation documentation. These reports are historical evidence, not claims of new load testing or deployed code adoption.

- `shipment-match-events-storage-investigation.md` measured **7,293,672** matching events at its final snapshot and reproduced redundant CATEGORY events from strict JSON object-key comparison. Current `ResolveJneCategories` compares `orderedObjectKeys` recursively, preserves list order/scalar types and skips unchanged category evidence. The fix is present in source; old historical events are not rewritten. The worker-recycle report records zero redundant growth in its bounded corrected-worker observation, not an indefinite guarantee. This task does not inspect loaded operational worker classes or restart them.
- `cross-customer-locking-remediation.md` records the coordinated fix in `ReconcilePickupProcessing` and `ReconcileCustomerPickupDay`. Current code separates owned and customer-attributed unowned discovery, uses explicit MySQL customer/AWB index scopes, then locks discovered IDs. These source changes are present. Native concurrent lock acceptance was not rerun here, and deployment adoption remains unverified.
- `ProjectJneShipments` still materializes report sources, builds matcher candidates, updates current pointers/versions for newer snapshots, and runs existing attribution work inside a report-wide transaction. When automation is enabled, its existing historical customer reconciliation continuation still runs on replay. This increment does not add such work to GET requests, increase its frequency or attempt unsafe dependency-based skipping. The measured 1,000-AWB unchanged import still makes 1,045 queries; it is not a streaming/scalable ingestion redesign.
- Observations remain one row per imported source row. Same-report replay adds zero observations; distinct repeated reports retain new observations even when they add zero transitions. Raw CSV/source storage therefore still grows. No retention/deletion/optimization is performed or implicitly authorized.
- Current registry selection uses the unique AWB index and existing list-order index. Customer/status/source-date filters have supporting existing indexes. Grouped summary counts necessarily scan qualifying records/index entries; large-scale summary latency is not certified. Receipt maxima use the observation shipment index but may examine all observations for each page's shipments. Default changes-only history can scan a shipment's observation range because `changes_current` is not in that timeline index. No speculative index is added without production-like measurement.
- Snapshot ordering protects tracking, not automatic ownership from every contradictory older identity source. Existing matching may flag conflicts from older evidence intentionally. Matching/admin review rules are untouched; the UI shows customer-match confidence beside retained pointers.
- The default refresh lookback still excludes old unresolved AWBs from routine selection. This page has **no lookback cap**, so they remain searchable. Snapshot freshness and pulling eligibility are distinct.
- Default scheduling bounds are 6,000 AWBs per job and 200 jobs per cycle in `config/jne-reports.php`. The theoretical selector ceiling is 1.2 million AWBs; exceeding it records an error instead of silently omitting the remainder. These finite limits do not establish sustainable provider/worker throughput. This increment creates no additional schedule and leaves those limits unchanged.
- Local queue config defaults to database, 90-second retry-after; import jobs use one try/60 seconds, reconciliation jobs four tries/60 seconds on `reconciliation`; documents/deliveries/mobile-push have separate existing consumers. A local combined consumer can still delay later queues under default backlog. No new jobs or queue settings are introduced. A running scheduler/adequate source capacity cannot be inferred from its configuration.
- Linux/systemd deadline/lease enforcement remains unaccepted. Prior Windows tests show a PHP worker can outlive its configured timeout without pcntl, allowing lease overlap. This task does not certify the operational 90-second lease, increase concurrency or prescribe a new timeout.

## 9. API, UI and idempotency behavior

New routes are `/admin/shipment-monitoring` and `/admin/shipment-monitoring/{shipment}`. They return Inertia pages, not a new public JSON API. Existing collector/worker APIs are untouched, so no external API contract, Postman workspace setup or simulation is required for these read-only queries. Postman API-engineer guidance was applied to preserve the existing boundary and keep local-vs-live evidence explicit.

Both endpoints require an authenticated **active admin_supervisor** before querying shipment details. Guest requests redirect to login; other roles/inactive admins get 403 without a shipment existence check. No customer portal or broader outlet/customer access was added. List requests hydrate at most **20 or 50** shipments; detail requests hydrate at most **25** history entries. Customer selection reuses the existing paginated picker rather than loading all customers.

Filters: literal escaped AWB prefix, customer ID, known normalized status, baseline active/terminal, optional source entry-date range, optional snapshot-age hours, stale/unobserved and page size. Date filtering uses **05:00 WIB inclusive through next-day 05:00 exclusive**, based on source entry date. Summary statistics use the same applied filters, including status/lifecycle. Never-observed and stale are distinct. No default stale threshold is invented; users can choose one for display. Terminal snapshots are not labeled stale. Choosing a threshold never changes source schedules.

Source status time, effective observation time and successful projection receipt are separate columns/labels. Delivery time is shown only when supported evidence populated it. Raw data/checksum/row/Hybrid provenance sit behind disclosure. List attribution confidence is visible; detail pages offer no correction controls. The list reload button only reloads stored data and does not submit a JNE request. Browser auto-polling was not added.

History semantics:

1. Same source/report replay: existing unique observation is retained, no new observation or transition.
2. Duplicate or unchanged distinct report: separate immutable source/observation, `changes_current=false`.
3. Case/outer or repeated whitespace/empty-vs-null differences: canonical comparison suppresses formatting-only transitions when normalized classification is unchanged; raw cells remain intact.
4. Newer meaningful raw status or normalized status: current source advances and transition is retained.
5. Older snapshot: observation is retained, does not change current state or create a current-transition event.
6. A → B → A and post-terminal correction: compare to the current predecessor, not all historical signatures; both transitions remain.
7. Same status with new timestamp/other source evidence: evidence remains accessible in the all-evidence view even if it is not a status transition.

The default history view filters existing `changes_current`; it represents changes applied when processing, not a reconstructed complete carrier timeline. Historical flags/events were not rewritten. Pre-existing false-positive flags from older code may therefore still appear.

## 12. Known limitations

- Existing long report transactions, per-AWB updates/matching, replay fanout and retained source/observation growth remain.
- No automatic alerts, exports, bulk operations, source refresh button or customer-facing access was added to the new screen.
